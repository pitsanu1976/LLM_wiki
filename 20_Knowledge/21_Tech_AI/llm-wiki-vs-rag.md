# LLM Wiki vs RAG

**ประโยคเดียว:** RAG **ค้นใหม่ทุกครั้งที่ถาม** — LLM Wiki **เข้าใจครั้งเดียวแล้วอัปเดตต่อ**

## เทียบกันตรง ๆ

| มิติ | RAG | LLM Wiki |
|---|---|---|
| ความรู้อยู่ที่ไหน | chunk + embedding ใน vector store | หน้า markdown ที่มนุษย์อ่านได้ |
| การสังเคราะห์เกิดเมื่อไร | ตอน query ทุกครั้ง | ตอน ingest + ตอนดูแล |
| ต้นทุนต่อคำถาม | สูง (ค้น + ประกอบใหม่) | ต่ำ (อ่าน index + หน้าทีเกี่ยวข้อง) |
| การสะสมความรู้ | ไม่มี — เริ่มจากศูนย์ทุกครั้ง | มี — หน้าสะสมและเชื่อมกันขึ้นเรื่อย ๆ |
| contradiction | มองไม่เห็น (chunk ไม่รู้จักกัน) | ถูกตั้งธงไว้ในหน้า wiki |
| คำถามที่ต้องสังเคราะห์ 5 เอกสาร | ต้องประกอบใหม่ทุกครั้ง | คำตอบถูกเขียนไว้แล้ว |
| คำถามที่ไม่มีใน wiki | RAG ยังตอบได้จาก chunk ดิบ | wiki ตอบไม่ได้ถ้ายังไม่ ingest |
| ความโปร่งใส | ต่ำ — เห็นแค่ chunk ที่ถูกดึง | สูง — อ่านหน้าเต็มได้ |
| การแก้ไข | แก้ที่ต้นฉบับแล้ว re-index | แก้ที่หน้า wiki (หรือ ingest ใหม่) |

## เลือกอะไรเมื่อไร

**ใช้ RAG เมื่อ:**
- คลังใหญ่และกว้าง ต้องการ recall สูง
- เอกสารเปลี่ยนตลอดและไม่ต้องการสังเคราะห์ข้ามเอกสาร
- ต้องการค้นแบบ exact match ในเนื้อหาดิบ

**ใช้ LLM Wiki เมื่อ:**
- ต้องการ **ความเข้าใจที่สะสม** ไม่ใช่การค้น
- โดเมนแคบ–กลาง (หลักร้อยหน้า) ที่อ่าน index ไหว
- ต้องการตรวจสอบได้ว่าความเชื่อมาจากไหน และขัดกันตรงไหน
- จะถามคำถามเดิมซ้ำในรูปแบบต่าง ๆ

## ไม่ใช่ศัตรูกัน

Karpathy เองแนะนำให้ใช้ **`qmd`** (search แบบ hybrid BM25 + vector พร้อม LLM re-ranking
ทำงานบนเครื่อง, index เดียวเป็น SQLite) เมื่อ wiki โตเกินกว่าที่ index ไฟล์เดียวจะไหว

พูดอีกแบบ: **wiki คือชั้นความเข้าใจ, search คือชั้นการเข้าถึง** — ใช้คู่กันได้
และในทางปฏิบัติ RAG ที่ดีมักกลายเป็น "wiki + retrieval" อยู่ดี

## ข้อควรระวัง

- RAG ที่ดูดีอาจทำให้เข้าใจผิดว่ามีความรู้สะสม — จริง ๆ มันแค่ค้นได้เก่ง
- LLM Wiki ที่ไม่มี lint จะเน่าเงียบ ๆ: หน้าเก่าขัดกับหน้าใหม่โดยไม่มีใครรู้
- ทั้งสองวิธีพังเหมือนกันถ้า **ไม่มีใครเปิดดู** — ปัญหาการ retrieve ไม่ใช่ปัญหาเดียว
  ปัญหาที่แท้จริงคือ *agent ไม่รู้ว่าตัวเองมีอะไร* → ต้องมี trigger/ดัชนีที่บังคับให้เปิด
