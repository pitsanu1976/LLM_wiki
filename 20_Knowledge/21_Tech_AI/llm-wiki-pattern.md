# LLM Wiki Pattern

**นิยามสั้น:** ให้ LLM สร้างและดูแลคลังความรู้ markdown ที่เชื่อมกันอย่างต่อเนื่อง
แทนที่จะไปค้นเอกสารดิบใหม่ทุกครั้งที่ถาม — ความรู้ถูก *compile* ครั้งเดียวแล้ว *keep current*

## องค์ประกอบขั้นต่ำ

1. **แหล่งดิบที่แก้ไม่ได้** — ถ้าแก้ต้นฉบับ ประวัติการอ้างอิงพัง
2. **หน้า wiki ที่ agent เป็นเจ้าของ** — summary, concept, entity, comparison
3. **schema** — กติกาที่เขียนไว้ ให้ agent ทำงานซ้ำได้เหมือนเดิมข้าม session

ถ้าขาดข้อ 3 จะได้แค่ "แชทที่ยาวขึ้น" ไม่ใช่ wiki

## สามปฏิบัติการ

```
ingest  →  query  →  lint  →  (วนกลับ)
```

- **ingest**: แหล่งใหม่ → สรุป → เชื่อม → อัปเดต index/log
- **query**: ถาม → อ่าน index → เจาะหน้า → ตอบพร้อม citation → **เก็บคำตอบที่ดีกลับ**
- **lint**: หา contradiction, orphan, หน้าที่ขาด, ลิงก์ที่ผิด

## ทำไมมันทำงานได้

ภาระที่ทำให้มนุษย์เลิกทำ wiki คือ **bookkeeping** ไม่ใช่การอ่านหรือคิด
การอัปเดต backlink, รักษา summary ให้สด, ตามว่า claim ไหนขัดกัน — งานพวกนี้
โตเร็วขึ้นเรื่อย ๆ ตามจำนวนหน้า แต่ LLM ทำได้ถูกและเร็วในต้นทุนที่เกือบคงที่

## ข้อจำกัดที่ต้องรู้

| ข้อจำกัด | ผลกระทบ |
|---|---|
| scale | index แบบอ่านทั้งไฟล์ไหวถึง ~100 แหล่ง/หลายร้อยหน้า เกินนั้นต้องมี search (เช่น qmd) |
| การ "ลืมว่าเคยจด" | agent อาจไม่เปิด wiki กลางงาน ถ้าไม่มี trigger ที่ชัดใน schema |
| ต้นทุนการตัดสินใจ | ตอน ingest ส่วนใหญ่ของ token หมดไปกับการเลือกที่เก็บ/merge ไม่ใช่การเขียน |
| คุณภาพ schema | schema กำกวม → agent จัดวางไม่สม่ำเสมอ → wiki เสื่อมสภาพช้า ๆ |

## หลักคิดที่สำคัญกว่าตัวเครื่องมือ

- **แยก "แหล่งความจริง" ออกจาก "ความเข้าใจที่ compile แล้ว"** — สองอย่างนี้ต้องมีที่อยู่ต่างกัน
- **คำถามก็มีค่าเท่าแหล่งข้อมูล** — คำตอบที่ดีต้องถูกเก็บกลับ ไม่ปล่อยหายไปใน chat history
- **ทุกอย่างเป็นไฟล์ข้อความธรรมดา** — อ่านได้ด้วยตา, diff ได้, ย้ายได้, เปิดด้วยเครื่องมืออะไรก็ได้
- **idea ไม่ใช่ software** — pattern นี้ตั้งใจให้ปรับรูปตามโดเมน ไม่ใช่ติดตั้งแล้วจบ
